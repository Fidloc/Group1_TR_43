## UC-02 «Увійти до системи»
 
| Поле | Опис |
|---|---|
| ID і назва | UC-02 «Увійти до системи» |
| Мета | Автентифікувати користувача та надати доступ до його подій і функцій організації заходів. |
| Основний актор | Учасник / Організатор |
| Тригер | Користувач відкриває веб-застосунок і хоче отримати доступ до свого облікового запису. |
| Передумови | Користувач уже зареєстрований (UC-01); обліковий запис активний. |
| Основний сценарій | 1. Користувач відкриває сторінку входу.<br>2. Вводить email і пароль.<br>3. Передає дані системі.<br>4. Система перевіряє, що обов'язкові поля заповнені й мають коректний формат.<br>5. Система перевіряє, що email і пароль збігаються з даними облікового запису.<br>6. Система створює сесію користувача.<br>7. Система відкриває головну сторінку зі списком подій користувача («Мої події», «Створити подію», запрошення до подій). |
| Альтернативний / помилковий сценарій | A1. На кроці 4 поля порожні або мають некоректний формат — система не виконує вхід і повідомляє, що саме потрібно виправити.<br>A2. На кроці 5 email або пароль невірні — система не виконує вхід і повідомляє про невірні дані (без уточнення, що саме помилкове). |
| Постумови | Успіх: сесію створено, користувач автентифікований і бачить свої події. Помилка: сесію не створено, користувач залишається неавторизованим. |
| Пов'язані вимоги | FR-01, FR-02 |
| Критерії приймання | AC-01, AC-02 |
| Додатковий Use Case | UC-01 «Зареєструватися»: якщо облікового запису немає, користувач переходить до реєстрації. Пов'язані FR-01 та AC-01. |

## UC-05 «Зареєструвати витрату»
 
| Поле | Опис |
|---|---|
| ID і назва | UC-05 «Зареєструвати витрату» |
| Мета | Додати до обліку події спільну витрату, щоб вона стала доступною для розподілу між залученими учасниками (UC-09). |
| Основний актор | Учасник (у тому числі Організатор) |
| Тригер | Хтось із учасників оплатив щось спільне (продукти, оренду, квитки) і хоче внести це в облік. |
| Передумови | Користувач авторизований і є учасником цієї події. У події є хоча б один учасник. |
| Основний сценарій | 1. Учасник відкриває сторінку події.<br>2. Обирає дію «Додати витрату».<br>3. Вводить суму та опис витрати.<br>4. Вказує, хто заплатив. За замовчуванням це він сам.<br>5. Підтверджує збереження.<br>6. Система перевіряє, що сума є числом і більша за 0.<br>7. Система зберігає витрату.<br>8. Система показує витрату в обліку події. |
| Альтернативний / помилковий сценарій | A1. На кроці 6 сума ≤ 0 або не є числом. Витрата не зберігається, система показує причину, і учасник може виправити суму.<br>A2. На кроках 2–5 учасник скасовує дію. Нічого не зберігається. |
| Постумови | Успіх: витрата є в обліку події й доступна для розподілу (UC-09). Помилка або скасування: облік не змінено. |
| Пов'язані вимоги | FR-09, FR-10 |
| Критерії приймання | AC-09, AC-10 |
| Додатковий Use Case | UC-09 «Розподілити витрату» виконується після UC-05 для вже збереженої витрати. |
 
Activity Diagram: [model/activity-uc-05.md](../model/activity-uc-05.md)

 ## UC-07 «Створити подію»
 
| Поле | Опис |
|---|---|
| ID і назва | UC-07 «Створити подію» |
| Мета | Створити нову подію з назвою, датою, місцем і описом; створювач стає її Організатором. |
| Основний актор | Організатор (авторизований користувач, який створює подію) |
| Тригер | Користувач хоче організувати захід і розпочинає створення нової події. |
| Передумови | Користувач авторизований (UC-02). |
| Основний сценарій | 1. Користувач обирає створення нової події.<br>2. Система показує форму події.<br>3. Користувач вводить назву, дату, місце й опис.<br>4. Користувач передає дані системі.<br>5. Система перевіряє, що назву вказано.<br>6. Система перевіряє, що дату вказано і вона не в минулому.<br>7. Система зберігає подію і призначає користувача Організатором.<br>8. Система показує підтвердження і сторінку події. |
| Альтернативний / помилковий сценарій | A1. На кроці 5 назву не вказано — система не зберігає подію і повідомляє про відсутню назву.<br>A2. На кроці 6 дату не вказано або вона в минулому — система не зберігає подію і повідомляє про некоректну дату. |
| Постумови | Успіх: подію збережено, вона відображається у списку подій, створювач має роль Організатора. Помилка: подію не створено. |
| Пов'язані вимоги | FR-03, FR-04; NFR-03 |
| Критерії приймання | AC-03, AC-04 |
| Додатковий Use Case | UC-08 «Редагувати подію»: ті самі перевірки назви й дати діють під час збереження змін (FR-04). |

## UC-09 «Розподілити витрату»
 
| Поле | Опис |
|---|---|
| ID і назва | UC-09 «Розподілити витрату» |
| Мета | Розподілити вже існуючу витрату між учасниками, яких Організатор обрав як залучених до неї. |
| Основний актор | Організатор |
| Тригер | Організатору потрібно визначити, хто з учасників повинен брати участь у витраті. |
| Передумови | Організатор авторизований і є тим, хто створив подію. У події вже є створена витрата з певною сумою (UC-05). Також у подію вже додані учасники. |
| Основний сценарій | 1. Організатор обирає потрібну витрату.<br>2. Система показує суму витрати і список учасників.<br>3. Організатор вручну обирає зі списку учасників, кого стосується ця витрата.<br>4. Організатор підтверджує розподіл.<br>5. Система перевіряє, що обрано щонайменше одного учасника.<br>6. Система ділить суму витрати порівну на всіх обраних учасників і обчислює частки з точністю до 0,01 грн.<br>7. Система перевіряє, що сума часток дорівнює сумі витрати.<br>8. Система зберігає розподіл.<br>9. Система показує частки та повідомляє про успіх. |
| Альтернативний / помилковий сценарій | A1. На кроці 5 не обрано жодного учасника — система не зберігає розподіл, повідомляє про помилку й повертає Організатора до кроку 3.<br>A2. На кроці 7 сума часток не дорівнює сумі витрати — система не зберігає розподіл і повідомляє про помилку розрахунку. |
| Постумови | Успіх: розподіл збережено. Помилка: попередній стан розподілу не змінено. |
| Пов'язані вимоги | FR-11, NFR-02; UC-06 враховує зміни |
| Критерії приймання | AC-11 |
| Додатковий Use Case | — |
