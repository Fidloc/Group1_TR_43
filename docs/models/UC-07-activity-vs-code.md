# UC-07: порівняння діаграми діяльності з реалізацією v1.0

Діаграма діяльності: [model/activity-uc-07.md](../../model/activity-uc-07.md). Код: `EventManagement.cs`, маршрут `POST /api/events` у Program.cs, клієнт `EventActions.cs`.

| Елемент діаграми | Як зроблено в коді | Висновок |
|---|---|---|
| Кроки 1–4: обрати створення, показати форму, ввести назву, дату, місце й опис, передати дані | Клієнт надсилає `POST /api/events` з полями `title`, `date`, `place`, `description` | Відповідає (у v1.0 консольний клієнт без форми, тому дані задаються в контрольному сценарії) |
| Рішення «Назву вказано?», A1 | `TryReadCreate` / `TryCreate` повертають `missing_title`, сервер — 400 | Відповідає. Назва з одних пробілів теж вважається невказаною |
| Рішення «Дату вказано і вона не в минулому?», A2 | Немає дати або вона не розбирається → `invalid_date` у `TryReadCreate`; дата раніше за сьогодні → `invalid_date` у `TryCreate`; 400 | Відповідає. Назва перевіряється раніше за дату, як на діаграмі. Порівнюється лише дата без часу, тому подія на сьогодні дозволена |
| Крок 7: зберегти подію і призначити Організатором | `events.Add` (стан `Created`, новий `InviteCode`) і `participations.Add` з роллю `Organizer` | Відповідає (FR-03) |
| Крок 8: показати підтвердження і сторінку події | 201 Created з `EventDetailsDto`; клієнт показує подію і список подій користувача | Відповідає |

## Чого немає на діаграмі, але є в коді

- 400 `invalid_request`, якщо тіло запиту не JSON-об'єкт, немає `organizerUserId` або поле має неправильний тип. Це технічна відмова на межі API.
- Генерація коду запрошення `InviteCode` (8 символів, унікальний) — потрібна для UC-04 (FR-07).

## Що поки не зроблено

- Перевірка, що `organizerUserId` належить зареєстрованому користувачу (404 `user_not_found`). Реєстрація (UC-01/02) робиться в іншій гілці; перевірку додамо після злиття. Місце позначене `TODO` у `EventManagement.TryCreate`.

Діаграму ЛР №3 не міняли: вона описує сценарій з боку користувача, і реалізація з нею збігається.
