## 1. Планування спринту

Забезпечити надійне постійне збереження даних застосунку в реляційній базі даних SQLite через Entity Framework Core, виконати архітектурне розділення обов'язків в API за патерном Repository та надати Організатору можливість редагувати збережені події UC-08.

### 1.3. Відібрана історія: US-01 «Редагування події організатором» UC-08
* **Роль:** Організатор події.
* **Мета:** Змінити назву, дату, місце проведення або опис раніше створеної події.
* **Користь:** Щоб актуалізувати інформацію про захід для всіх учасників без потреби створювати нову подію та заново збирати людей.

#### Критерії приймання:
1. **AC-01 Успішне редагування:** За умови, що подія перебуває у стані `Created`, коли Організатор надсилає нові коректні дані, система оновлює запис у базі даних, повертає статус `200 OK` з оновленими деталями події, і зміни зберігаються після перезапуску сервера FR-03, FR-04, FR-06.
2. **AC-02 Відхилення некоректних даних:** За умови, що нове поле назви порожнє або нова дата вказує на минуле, система відхиляє запит зі статусом `400 Bad Request`, `missing_title` або `invalid_date` і не змінює попередні дані події FR-04.
3. **AC-03 Захист прав доступу:** За умови, що запит на редагування надсилає користувач, який не є Організатором цієї події, система відхиляє запит зі статусом `403 Forbidden`, `forbidden_not_organizer` FR-06.
4. **AC-04 Захист неактивної події:** За умови, що подія перебуває у стані `Closed` або `Cancelled`, система блокує будь-які зміни зі статусом `409 Conflict`, `event_not_active` FR-15.

### 1.5. Умови готовності інкременту
1. Код реалізовано відповідно до архітектурних контрактів та розподілу обов'язків (Single Responsibility / Repository Pattern).
2. База даних SQLite створюється автоматично через міграції Entity Framework Core (`dotnet ef database update`).
3. Дані зберігаються персистентно і залишаються доступними після повної зупинки та перезапуску веб-сервера.
4. Усі критерії приймання відібраної історії `US-01` виконані та перевірені на практиці.
5. Усі наявні та нові модульні тести проходять успішно.
6. Код пройшов Code Review у Pull Request та затверджений іншим учасником команди.
7. Інструкцію запуску в `README.md` оновлено командами налаштування БД та міграцій.

## 2. Підсумок спринту

### 2.1. Мета S1
Забезпечити постійне збереження даних у SQLite через EF Core, відокремити доступ до даних за патерном Repository та реалізувати редагування події Організатором (UC-08).

### 2.2. Прийняті історії
| ID | Історія | Результат |
|---|---|---|
| US-01 | Редагування події організатором (UC-08) | Прийнята. Критерії AC-01–AC-04 перевірені вручну через клієнт, зміни зберігаються після перезапуску сервера. |

### 2.3. Незавершене
- US-02 «Пошук та фільтрація подій» — не відбиралася до S1, залишена в беклозі для S2.
- TASK-07 виконана частково: додано тести InMemory-сховища, але тести `SqliteEventOrganizerRepository` та автоматичні тести AC-01–AC-04 для UC-08 ще не написані. Критерії приймання UC-08 перевірені вручну через клієнт. Задачу повернуто до беклогу (поле Sprint очищено) і буде відібрано до S2.

### 2.4. Результат демонстрації
- Через вебінтерфейс створено подію, відредаговано назву, дату та місце (AC-01), отримано `200 OK`.
- Перевірено відмови: порожня назва → `400 missing_title`, редагування не Організатором → `403 forbidden_not_organizer`, редагування закритої події → `409 event_not_active`.
- Повторено попередній сценарій UC-05 «Зареєструвати витрату».
- Сервер зупинено й запущено знову з тим самим файлом `eventorganizer.db` — створені записи та відредагована подія залишилися доступними.

**Практичний наслідок:** у v1.0 після перезапуску всі дані зникали, бо зберігалися в `List<T>`. Тепер дані зберігаються у файлі SQLite, і користувачам не потрібно заново створювати події та вносити витрати.

### 2.5. Причина труднощів
Основну частину змін (сховище, контекст, міграцію та ендпоінти) внесли однією великою гілкою, а не окремими гілками по задачах. Через це було складно рецензувати зміни й відстежувати внесок кожного учасника, а діаграму класів довелося узгоджувати з міграцією вже після реалізації (у ній було поле `OrganizerUserId`, якого немає в таблиці).

### 2.6. Наступне покращення (ретроспектива)
У S2 кожну технічну задачу виконувати в окремій гілці з окремим PR, а спільну модель даних (діаграму класів) погоджувати до початку паралельного редагування коду.

### 2.7. Інтегрований стан
Посилання на коміт `main` буде додано після злиття PR.
